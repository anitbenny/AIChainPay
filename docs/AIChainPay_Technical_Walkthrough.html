1. Problem, goal and fundamentals

A blockchain transaction normally needs an account's private-key signature. In a conventional DApp, a user revisits the website and approves every payment in MetaMask. An AI chat cannot safely or legitimately possess the owner's MetaMask key. AIChainPay therefore separates one-time owner authorization from routine bounded payment execution.

The owner deposits small Sepolia test ETH into a Solidity vault and signs a grant for a separate agent address. That grant has an aggregate allowance, per-payment cap, expiry and optional recipient list. The owner can revoke it. A ChatGPT user authenticates as that wallet through SIWE and OAuth, asks MCP tools to prepare a payment, reviews an exact in-chat card and clicks Confirm. The agent signs the resulting vault call and pays gas. The contract, not the AI model, independently enforces the grant. Routine approval does not return to the website.

Terminology: an EOA is a private-key-controlled account; wei is the smallest ETH unit (1018 wei = 1 ETH); gas pays transaction computation; a smart contract is public on-chain code; an ABI tells ethers.js how to encode calls and decode events; a receipt proves a transaction was mined, while a prepared preview does not.

Not PayBox itself. This is a PayBox-inspired experience using a Solidity vault and dedicated agent signer. It does not use PayBox custody/MPC infrastructure. It never transfers routine payments directly from the owner's ordinary MetaMask balance.

2. Architecture, identities and multi-user behavior

Owner MetaMask ─ connect/SIWE ─▶ React dashboard ─ HTTPS ─▶ Connector + SQLite
       │                              │                    ▲
       ├─ deposit/grant/revoke ───────┼──────────▶ Sepolia vault
       │                              │                    ▲
       └─ no owner key in backend     └─ read views       │ agent-signed call
                                                         │
ChatGPT ─ OAuth/PKCE ─▶ /mcp tools ─ prepare/card/click ─▶ signer
Sepolia vault ─ ETH transfer + PaymentExecuted event ─▶ recipient

Owner: signs login message and setup transactions in MetaMask. Deployer: signed the one-time contract deployment; it has no privileged user-spending role. Agent: one configured backend signer, paid Sepolia ETH for gas, can spend only a given owner's deposited credit under that owner's on-chain grant. Recipient: receives actual ETH from the vault, not from ChatGPT or from the agent wallet.

The deployed contract is not hard-coded to the original wallet. In contracts/AIChainPay.sol, balances[msg.sender] credits each depositor, and permissions[owner][agent] separates grants. connector/src/auth/siwe.ts accepts any valid supported EOA signature, creates that wallet's session, and connector/src/payments/prepare.ts scopes requests to the authenticated owner and OAuth client. A second person can use the same contract and hosted connector with their own MetaMask EOA, but starts with zero vault credit and no grant. They must deposit their own test ETH and authorize the configured agent. A smart-contract wallet is rejected by v1 SIWE login. The Solidity suite includes a positive second-owner deposit/grant/agent-payment case and checks the first owner's credit is unchanged. The second person's full browser/chat workflow was not separately manually demonstrated.

3.2 Chat balance read

ChatGPT connects to the public HTTPS /mcp via OAuth. The connector's createOAuthProvider() handles authorization code + PKCE and wallet-linked consent; verifyBearer() checks token expiry, audience and scope on every MCP request. createMcpServer() binds tools to the token's owner. get_contract_balance calls ChainService.balance(owner), which reads contract getBalance(owner). A JSON result returns wei/ETH. The connector writes an mcp_request audit row in SQLite; the balance itself is read from Sepolia and no transaction is sent. get_native_balance is different: it reads ordinary wallet ETH.

4. Solidity contract function-by-function

Source: contracts/AIChainPay.sol; exported interface: packages/shared/src/AIChainPay.abi.json and packages/shared/src/index.ts. The actual ABI names below are the deployed design.

Function / statePlain-language behavior and checks
receive(), fallback()Reject an ordinary direct ETH send or unknown call. ETH can still be forcibly sent at EVM level; forced surplus does not create a user's credit.
deposit()Payable, requires nonzero msg.value; credits balances[msg.sender], increases totalLiabilities, emits Deposited. No special owner address exists.
withdraw(amount)Owner withdraws their own credited ETH, nonzero and not beyond balance. Decrements accounting before transfer; reverts on failed transfer; protected by nonReentrant.
getBalance(owner) / public balances(owner)Read per-owner vault credit; anyone can read public chain state, but only the owner controls withdrawal/grant.
grantAgent(agent,totalAllowance,maxPerPayment,expiresAt,recipients)Caller grants their own funds only. Agent cannot be zero/vault/self; total and max positive, max ≤ total; expiry must be future; ≤20 distinct valid recipients. Replaces grant, increments epoch, emits AgentGranted. Empty list means unrestricted recipients.
revokeAgent(agent)Caller invalidates their grant to that agent: advances epoch, sets inactive/zero limits and emits AgentRevoked. A later grant is possible; old requests with old epoch remain stale.
getAgentPermission(owner,agent)Read active flag, remaining allowance, maximum, expiry, epoch and recipient policy.
isAllowedRecipient(owner,agent,recipient)Read whether current epoch's list permits recipient; if unrestricted, returns true. Other payment checks still apply.
pay(recipient,amount,memo,requestId)Optional direct owner-signed payment from their vault credit. Not the AI path. Calls the shared validation/execution code and is non-reentrant.
executeAgentPayment(owner,recipient,amount,memo,requestId,permissionEpoch,requestDeadline)Agent-only delegated route: active grant for (owner,msg.sender), current time before grant expiry, matching epoch, request not past deadline, valid payment, amount within max and remaining allowance, recipient allowed. Decrements allowance, then executes; non-reentrant.
_validatePayment(...)Requires positive amount; recipient not zero, vault or owner; nonzero unused bytes32 request ID; memo ≤140 UTF-8 bytes; enough owner vault credit.
_execute(...)Deducts owner credit/liabilities, marks request ID used, stores payment/participant indexes, calls recipient with exact ETH, reverts if transfer fails, emits PaymentExecuted. A revert rolls all preceding changes back.
getPaymentCount(participant), getPayment(participant,index)Read recorded payments involving an owner/recipient; out-of-range index reverts. Not full wallet history.

Public getters: totalLiabilities(), usedRequestIds(owner,id), MAX_MEMO_BYTES() and MAX_ALLOWED_RECIPIENTS() are compiler-generated for public state/constants. Event and account data are public on Sepolia; do not put secrets in memos.

7. Safety, failure modes and trust limits

  • Two separate permissions: OAuth authorizes ChatGPT to call an owner's tools; the Solidity grant authorizes the agent to spend this owner's vault credit. Browser logout or plugin disconnection does not revoke on-chain permission.
  • One-use exact confirmation: the card capability is private UI metadata and stored only hashed. The server binds it to request/digest, owner, OAuth client, mode and deadline. Verify-only approvals cannot become live approvals. The model cannot supply a simple approved:true.
  • Human-proof limit: the host must isolate private metadata and enforce app-only callback visibility. The component's event.isTrusted is not server-verifiable human attestation. A malicious host/backend or stolen full OAuth access may defeat this layer; on-chain allowance/cap/expiry/revocation limit damage.
  • Crash/nonce safety: durable signed bytes and unique nonce prevent a restart from creating another payment for the same request. Do not use the agent key for unrelated transactions while the connector runs. A mismatched/reorganized receipt needs investigation, not blind retry.
  • Public data: recipient, amount, memo and events are public on Sepolia. Do not put secrets in memo. Use only small test funds.
  • Revocation: once mined, it blocks future delegated execution under that grant. It cannot undo completed transfers and cannot guarantee ordering ahead of an already-pending agent transaction. A later grant creates a new epoch.
  • Availability: if backend or tunnel stops, chat tools stop; already-deployed contract and credited ETH remain on Sepolia. A stable HTTPS host can replace ngrok. Local SQLite and agent key must be protected and backed up; copying only Git files to a new machine does not transfer existing OAuth sessions or grant authority to a different agent.

8. Running and demonstrating AIChainPay

8.1 Existing validated Windows workspace

Prerequisites: Node.js ≥22.13, npm, this repository with its existing ignored local RPC/connector configuration, assigned ngrok HTTPS hostname and sufficient agent gas. Do not start a second connector on port 3000. The currently deployed contract is reused; no deployment transaction is needed. Run these in PowerShell from the repository:

cd D:\AIChainPay
npm.cmd ci
npm.cmd run build
npm.cmd run verify:sepolia
npm.cmd run start:sepolia -- --live

The explicit live switch works only for the already verified local connector: scripts/sepolia-connector.ts requires locally recorded real-host verification approval and rejection, matching agent key and live adapter settings. A new installation must first use npm.cmd run start:sepolia, which forces execution disabled. Never set verification flags merely to bypass the gate.

In another PowerShell window, only if the tunnel is offline:

cd D:\AIChainPay
.\scripts\start-stable-ngrok.ps1 -PublicBaseUrl https://upscale-nanometer-duvet.ngrok-free.dev -AllowLiveConnector

Enter ngrok authentication only in its hidden local prompt. Keep connector and tunnel windows open. Check https://upscale-nanometer-duvet.ngrok-free.dev/health; the dashboard is the same origin and ChatGPT's OAuth MCP URL is https://upscale-nanometer-duvet.ngrok-free.dev/mcp. An unauthenticated /mcp request should return a bearer challenge, not payment data. This assigned hostname belongs to the operator's ngrok account; it is not guaranteed on another device.

8.2 Fresh operator machine versus a second end user

Fresh operator machine: build from the lockfile; place a Sepolia RPC URL in a private local root .env based on .env.example; verify deployed manifest/bytecode with npm.cmd run verify:sepolia; acquire a stable public HTTPS origin; run npm.cmd run setup:sepolia-connector -- https://YOUR-HTTPS-ORIGIN once. This makes a new agent signer and local SQLite/OAuth state without broadcasting. Fund that new agent with small Sepolia test ETH for gas and have each owner grant that agent. Start disabled; only after genuine card verification can the guarded live route be enabled. Never copy/publish private keys, SQLite, signing JWK or tokens. A deployer private key is not necessary to reuse this contract.

Second end user: does not run the backend if the operator hosts it. They open public dashboard, connect a MetaMask EOA on Sepolia, sign the SIWE login message, deposit their own test ETH, grant the displayed agent with total allowance/cap/expiry (optional allowlist), then OAuth-connect their own ChatGPT plugin to the same /mcp endpoint. Their old ordinary wallet ETH remains outside the vault. Without deposit/grant, they can read a zero balance but cannot pay. Another person's grant cannot spend their vault credit.

10. Fifteen viva questions and answers

  1. Why a vault instead of paying directly from MetaMask? An AI backend cannot sign as the owner's wallet without taking its private key. The owner deposits only test funds and delegates bounded contract authority.
  2. Why does the deployer need a private key? Deployment is a transaction that must be signed and funded. The deployed contract has no deployer-only spending role.
  3. Why does the agent need a private key? It signs executeAgentPayment and pays gas. Its key cannot call withdraw for someone else's credit.
  4. Why is the owner key only in MetaMask? Owner deposit, grant, revoke and withdrawal require that person's consent; the backend does not import their key.
  5. Can my evaluator use another wallet? Yes, a supported EOA can create its own credit/grant on the same contract. It must do its own SIWE login, deposit and grant. A contract-account wallet is not supported by current login.
  6. What does SIWE do? A short-lived signed message authenticates control of a wallet to the dashboard; it is not an ETH transaction or agent grant.
  7. How is OAuth different? OAuth gives the chat client scoped API access for that wallet. The Solidity grant independently governs actual vault spending.
  8. Why MCP? It gives ChatGPT named read, prepare, card and status tools over a standardized remote connection.
  9. Why ngrok? The local connector needs public HTTPS for cloud ChatGPT and OAuth. Ngrok forwards to this laptop; stable hosting can replace it. It does not hold vault ETH.
  10. What happens if the backend stops? Chat reads/payments stop, but contract credit and past transactions remain on Sepolia. Owner can later restart or use another compatible interface.
  11. What prevents over-limit payments? Contract checks credit, remaining allowance, per-payment cap, expiry, epoch and optional recipient list on every delegated transaction.
  12. What prevents duplicates? Prepared idempotency key, one-use card token, SQLite state/nonce journal and on-chain used request ID. Identical signed bytes can be rebroadcast after uncertainty without a new payment.
  13. How does revocation work? Owner signs revokeAgent; after mining, grant is inactive and epoch advances. A later grant creates a new epoch; completed payments cannot be reversed.
  14. Does the contract know a human clicked? No. The server trusts ChatGPT's UI isolation and one-use callback; Solidity knows only agent signature and on-chain limits.
  15. What proves payment success? Mined receipt with expected sender/vault/calldata, matching PaymentExecuted event, recipient ETH increase and reconciled confirmed status—not a prepared preview or AI statement.
