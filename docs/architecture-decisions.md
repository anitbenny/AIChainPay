## 2026-10-19 design checkpoint: explicit in-chat confirmation card

The native tool-approval experiment did not establish fresh execution confirmation. A supported-protocol MCP Apps card is now implemented using the current [official UI guide](https://developers.openai.com/plugins/build/chatgpt-ui), [quickstart](https://developers.openai.com/plugins/build/app-quickstart) and [metadata reference](https://developers.openai.com/plugins/reference). No extra SDK dependency or owner-custody/website-approval change was introduced. Model-visible show-card and app-only decision tools use widget-private one-use capabilities bound to exact intent and identity. The trust boundary is the chat host and backend, not cryptographic proof of a human. The card adapter is tested locally and remains disabled pending real account verification. See [implementation details](./confirmation-card.md).

The dedicated agent is now generated locally but not loaded/funded. Real ChatGPT Sepolia reads, MetaMask owner deposit/grant and the stable ngrok endpoint are verified; older observations below are retained as history. GitHub remains unpublished. Current CI uses the official checkout/setup-node v7 examples with Node 22; no deployment keys are configured.

1. **Two network modes, no silent fallback.** Production accepts Sepolia chain ID 11155111 only; chain 31337 requires explicit `ALLOW_LOCAL_CHAIN=1` and is for development tests. The connector checks RPC chain ID, nonempty bytecode, vault ABI identity and the exact deployment code hash on Sepolia before serving. MCP tools cannot choose RPC, chain or contract.
2. **Vault delegation.** MetaMask retains the owner key and signs setup actions. A separate backend agent pays its own gas and may spend only credited vault ETH under the contract's bounded, expiring, revocable grant. A new grant replaces the old one and increments its epoch. Owner-as-recipient is rejected to avoid duplicate participant indexing. No upgradeable proxy, privileged drain or ordinary-wallet spending is implemented.
3. **Compatible pinned versions.** Node 22.22.2 was available and satisfies [Hardhat 3's Node 22.13+ requirement](https://hardhat.org/docs/getting-started). Current registry versions were queried and pinned: Hardhat 3.20.0 with `@nomicfoundation/hardhat-toolbox-mocha-ethers` 4.0.0, Solidity 0.8.28, ethers 6.17.0, OpenZeppelin Contracts 5.6.1, TypeScript 5.9.3, MCP SDK 1.32.1, `oidc-provider` 9.12.2, `siwe` 3.0.0, `better-sqlite3` 12.4.1, Express 5.3.0, React 19.3.1, Vite 8.3.4, plugin-react 6.1.2, Tailwind 4.3.3 and zod 3.25.76. SQLite 13.0.3 failed a clean install on this Windows host because its native build required a missing C++ toolset; 12.4.1 installed and loaded after clean `npm.cmd ci`. Zod v3 is used with the published MCP SDK v1 API. Exact direct/transitive resolution is in [package-lock.json](../package-lock.json). Sources: [Hardhat ethers tests](https://hardhat.org/docs/guides/testing/using-ethers), [Hardhat deployment](https://hardhat.org/docs/guides/deployment/using-scripts), [ethers v6](https://docs.ethers.org/v6/), [OpenZeppelin 5.x](https://docs.openzeppelin.com/contracts/5.x/), [official MCP TypeScript SDK](https://ts.sdk.modelcontextprotocol.io/server).
4. **ChatGPT first, evidence-gated execution.** [OpenAI's custom-MCP guide](https://developers.openai.com/plugins/build/mcp-server), [auth guide](https://developers.openai.com/plugins/build/auth) and [connection guide](https://developers.openai.com/plugins/deploy/connect-chatgpt) support the selected remote MCP/OAuth path. The real ChatGPT account installed the plugin, completed OAuth and displayed a wallet/vault balance read; matching authenticated tool calls appear in connector audit. Payment approval remains unverified. MCP [elicitation rules](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation) exclude form-mode financial authorization, so the preferred in-band form approach is not used. The candidate adapter is ChatGPT's native per-write approval; the server trusts the client and receives no click proof, and ChatGPT may remember a tool approval within a conversation. It is disabled by default. Claude is unverified.
5. **Wallet-linked OAuth.** A one-use [SIWE](https://eips.ethereum.org/EIPS/eip-4361) challenge verifies an EOA. `oidc-provider` handles OAuth authorization code/PKCE, token persistence, discovery and resource audience; the app handles wallet login and scoped consent. Production client registration targets ChatGPT's Client ID Metadata Document route; a fixed local client is only for protocol tests. OAuth disconnection never revokes Solidity permission.
6. **One-origin single-instance deployment.** The connector serves built frontend, browser API, OAuth and MCP under one HTTPS origin; Vite uses a development proxy. SQLite uses WAL, migrations and persistent disk for one backend writer. An in-process signer queue plus database CAS, unique nonce and signed-before-broadcast persistence prevent the tested duplicate/race cases. Multiple backend writers or a shared agent used elsewhere require a redesigned distributed nonce coordinator, not just another server replica.
7. **Event and receipt truth.** The indexer scans `PaymentExecuted` from the actual deployment block in bounded batches, overlaps recent blocks for shallow reorgs, keys cursors by chain/contract, and reports incomplete catch-up. Request state and payment events are distinct. Receipt reconciliation checks actual signer, chain, target, nonce, zero-value calldata matching the stored intent, and matching event including memo; it never invents a successful transfer or equates `submitted` with `confirmed`.
8. **Secrets and deployment.** Separate root deployment-only `.env` and connector `.env` keep deployer and agent identities apart; Vite variables are public. OAuth signing JWK, SQLite and all secret-bearing files are Git-ignored. The agent signed payload is encrypted before SQLite persistence. The local screenshot is explicitly chain 31337 evidence. A separate Sepolia manifest now records the verified chain-11155111 deployment; no agent or GitHub remote is configured.
9. **Stable development ingress.** The account-free Cloudflared Quick Tunnel hostname died during ChatGPT OAuth testing. Its process kept retrying after the user cancelled a Windows notification, so process termination is ruled out but notification/network causality is unproven. With no Cloudflare-managed domain, an account-assigned [ngrok static development domain](https://ngrok.com/blog/free-static-domains-ngrok-users) is the test-session ingress for the connector and browser-facing OAuth on one origin. It carried a real authenticated ChatGPT read on the local chain; it has not yet carried a Sepolia read or payment. [OpenAI Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) would carry MCP traffic but does not itself expose this authorization server to the browser.
