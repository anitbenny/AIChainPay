# In-chat confirmation card implementation

This is a real MCP Apps component, not a standalone fake chat UI. Its **local implementation is tested**; actual ChatGPT rendering and verification-only approval AND rejection were observed on 2026-10-20 and matched to the persisted audit. A separate fresh live-card decision led to a [confirmed Sepolia payment](https://sepolia.etherscan.io/tx/0x2bfe8bfc442c084cc012fed2b345044819bad1a11dfef682fea7a7e0cbff01cf); the available screenshot below remains verification-only. It is served as `ui://aichainpay/payment-confirmation-v1.html` with `text/html;profile=mcp-app`. The bridge follows the official [MCP Apps UI quickstart](https://developers.openai.com/plugins/build/app-quickstart) and [UI metadata reference](https://developers.openai.com/plugins/reference), consulted 2026-10-19.

The [real ChatGPT screenshot](./screenshots/chatgpt-card-verify-approved.png) shows request `90af5a93-e34e-4c3d-9bf1-2f8039aab8d9`, exact intent and recorded verify approval with null transaction hash. The host also shows “CSP off”; host CSP enforcement and comprehensive metadata isolation were not independently established. Successful callbacks do not remove the trust boundary below.

`show_payment_confirmation` is model-accessible and creates off-chain confirmation state. It exposes the stored preview and verify/live label in structured content; its random capability is only in result `_meta`. The HTML has no embedded capability. `confirm_payment_card` has `_meta.ui.visibility: ["app"]` and truthful write annotations. The host must enforce private metadata and app visibility; these are explicitly trusted boundaries, not independently proven by the server.

SQLite stores only the capability hash, user, OAuth client, immutable request/digest, expiry, mode and decision/use timestamps. Issuing a replacement supersedes old capabilities for that request. Confirm/Reject checks all bindings atomically and rejects expired, used, superseded, mode-changed or mismatched capabilities. Verification decisions are consumed immediately and cannot authorize a later live transfer. Live decisions are consumed by the execution adapter, then the existing vault checks, simulation, gas check, nonce queue and encrypted signed-transaction journal apply. A rejection terminates the prepared request without broadcasting.

Rendering alone sends no action. The component uses textContent for all user fields, no external assets or connections, and accepts bridge messages only from its parent. Only a trusted DOM click invokes its app-only callback. `event.isTrusted` is a component-side guard, not a server-verifiable attestation. A malicious host/backend or stolen full OAuth access can defeat the host trust boundary; the owner still relies on on-chain limits and revocation. Nothing here is cryptographic proof that a person approved.

The default launcher forces execution disabled and loads no signer. A separately gated live launcher requires the operator's recorded real-host check and verification-mode approve/reject audit entries, then reads the ignored key locally. These checks reduce accidental enablement; they do not establish account compatibility by themselves.

Tests: backend capability isolation/replay/mode/expiry/rejection, SDK metadata/resource integration, synthetic-host browser interactions, local-chain signing and negative cases. The screenshot [local card render](./screenshots/confirmation-card-local-test.png) is labelled synthetic and is not ChatGPT evidence. No native approval bypass, website approval, generic signing tool or mainnet support was added.
